Madrid Night Noise and Terraces Explorer

Application requirements and interface mock-ups. This is a proposed exploratory application, not a legal compliance or causal attribution tool.

1. Application overview

Madrid Night Noise and Terraces Explorer is a web application that places the hospitality terraces registered in the City of Madrid's premises census next to the nighttime sound levels recorded by the city's fixed acoustic monitoring stations in the same month. It answers one main question:

How many terraces registered as open were near each acoustic monitoring station, and what nighttime sound levels did that station record during the same month?

The application joins terrace records, fixed monitoring stations, and daily acoustic observations using stable identifiers, dates, and a documented spatial proximity rule.

Linked-data value

The raw CSV files cannot answer the main question on their own. The daily file identifies stations only by code, the station locations are in a separate catalogue, terraces are located through the coordinates of their premises, and no file relates a station to the terraces around it or provides a combined same-month view. In the knowledge graph, stations, observations, terraces, premises, and districts become persistent resources, station-to-terrace proximity links are explicit, and districts are linked to an external knowledge graph (Wikidata). Each competency question then becomes a reproducible query instead of a manual cross-file join.

3. Data and initial scope

The first release covers one documented month with a terrace census snapshot and matching daily observations. Additional months can be added from the municipal archive after the first data join is verified.

IDSourceFields usedRole
D1Daily acoustic observationsStation code, year, month, day, Periodo=N (night, 23:00–07:00), LAeq in dB(A)Nighttime readings for the selected month.
D2Acoustic station catalogueStation code (e.g. RF-03), name, location, district, neighborhood, coordinatesMonitoring-point location and context.
D3Terrace census and monthly archiveid_terraza, id_local, terrace status (desc_situacion_terraza), premises coordinates, mesas_es, mesas_ra, load date (fx_carga)Same-month snapshot of registered terraces and authorized tables.

All selected municipal CSV resources state a CC BY 4.0 license on their resource pages. A terrace point represents the approximate entrance to its premises, not the exact terrace footprint. Census coordinates are UTM (ED50 until 15 September 2017, ETRS89 after that date), and the station catalogue gives both UTM and latitude/longitude, so distances are computed only after coordinates have been checked and converted to a common coordinate reference system.

4. Competency questions

The knowledge graph must be able to answer these questions. They will guide the SPARQL queries in later hands-on assignments.

  • CQ1. For a selected month and station, which terraces registered as open are within 250 m, and how many distinct terraces are there?
  • CQ2. What daily nighttime LAeq values were recorded at that station during the same month, and on how many days are usable values available?
  • CQ3. How do terrace counts and the median of daily nighttime readings vary across the monitored stations for the selected month?
  • CQ4. Which district and neighborhood contain a station, and which verified external district entity can it be linked to?

6. Non-functional requirements

NFR1The data pipeline records the source URL, download or snapshot date, selected month, and cleaning rules. The user interface credits the City of Madrid and links to the CC BY 4.0 license.

Proximity relationships may be precomputed so the SPARQL queries do not depend on special geospatial functions.
NFR3The interface is usable on desktop and mobile, with text labels for map markers, readable charts, keyboard access, and a table or list alternative to visual marks.
NFR4Invalid coordinates and unavailable measurements are excluded from calculations and reported as missing. No value is invented or interpolated.
NFR5Results are described as proximity and descriptive association. The interface does not claim legal non-compliance, a citywide noise level, or causation by terraces.

7. User interface description and mock-ups

The application is a web interface with three screens. The user starts with a point map, selects a monitoring station, then examines its nighttime series and nearby terrace records. A separate comparison screen places all eligible stations in one descriptive plot.

  • Explore (mock-up 1): month, district, and radius controls; a map with station points, terrace markers, and the 250 m circle; and a station list as a text alternative. Selecting a station opens its detail (FR1–FR3).
  • Station detail (mock-up 2): the station's context and linked district entity, summary figures, the daily nighttime LAeq chart with visible gaps, and the table of nearby terrace records (FR3–FR6).
  • Compare (mock-up 3): one point per station, plotting terrace count against the median of daily nighttime readings. Selecting a point opens that station's detail (FR7).

Each screen links to the sources and method behind its results (FR8, NFR5). These wireframes show layout and actions; their marks are illustrative, not measurements.

8. Interpretation boundaries

  • Proximity is measured from a station to the approximate entrance of premises. It does not identify the actual terrace footprint or establish a noise source.
  • A fixed station describes its measurement point. Its readings cannot be assigned to every nearby street, home, or district.
  • The terrace census is a status snapshot. “Registered as open” does not prove that a terrace operated on a particular night or when its authorization was first granted.
  • A daily LAeq reading cannot by itself establish that a legal acoustic objective was breached. This application does not display a legal-compliance badge.
