Method. A Python script that uses pandas reads each CSV as text, without modifying it, and computes for every column what the facets of OpenRefine show: type, distinct values with counts, range and blank cells. It also checks the relations between columns, within each file and across the three datasets. OpenRefine was not used. The files were downloaded on 1 October 2026; D1 and D3 are updated weekly, so the figures describe these files and not the current version of the portal.

  • D1. The portal page has no field dictionary (its references point to unrelated datasets): the columns are interpreted from their names and values.
  • D2. The page describes 8 of the 12 columns (the four area columns only for the 2016 structure), and the files from 2019 are not comparable with 2016.
  • D3. Street trees only: trees in zones and parks are separate datasets. Since 23 March 2021 trees in states that add no value are not published.

1.3 Cross-dataset analysis

  • Join keys. The 10 district codes and 73 neighbourhood codes are the same in D1, D2 and D3, and every neighbourhood belongs to the same district in the three datasets. The datasets are joined on codes, never on names.
  • Names. D3 writes the area names in upper case; D2 abbreviates Sants, Sarrià, Horta; and neighbourhood 13 is la Marina de Port in D1 and D2 but LA MARINA DEL PORT in D3. Area labels should come from one source.
  • Identifiers. The formats do not overlap (D1 integers of 8 to 11 digits, D2 NN-NNN, D3 seven digits followed by AR) and no value occurs in two datasets.
  • Coordinates. The datasets cover the same area (latitude 41.345 to 41.467, longitude 2.089 to 2.228): 550 of 550 shelters and 1,748 of 1,760 fountains lie inside the extent of the tree file. Converting latitude and longitude to EPSG:25831 with pyproj 3.8.0 reproduces the X and Y columns to within 0.008 m. D2 and D3 do not state the system of latitude and longitude, so WGS84 is an assumption.

3. Resource naming strategy

The strategy defines how the ontology terms and the individuals of the generated dataset are identified. It follows four steps: the URI form (hash or slash), the domain, the paths, and the pattern for classes, properties and individuals.

3.1 Decisions

DecisionChoiceReason
URI form for ontology termsHashThe ontology is small, so one request returns the whole model and a client can read all the terms at once.
URI form for individualsSlashThe dataset is large (550 shelters, 1,760 fountains, 145,034 trees) and updated regularly (weekly for shelters and trees, yearly for fountains). Each resource is requested on its own, and its description can be served as a separate information resource.
Domainhttps://w3id.org/barcelona-heat-relief/The project does not control a domain of its own, so a w3id.org permanent identifier is used. If the data moves to another server, only the w3id redirect rules change and the URIs stay the same. The path is not registered yet: it is requested when the dataset is published.
Path for ontology terms/ontology/HeatRelief#Separates the model from the data. Pattern: [domain]/ontology/[ontologyName]#[term].
Path for individuals/resource/{ClassName}/{identifier}Separates the data from the model. The class name in the path means that identifiers of different classes never collide.
Property URIs/ontology/HeatRelief#{propertyName}Properties are defined independently of classes: they are never nested under a class path.
Naming conventionsUpperCamelCase for classes, lowerCamelCase for propertiesClass names are also used as path segments of individuals. Labels are in English only.

3.3 Rules for the identifiers

  • Source keys. Identifiers come from the stable, unique keys of the sources, never from names, addresses or districts, which change and contain accents and spaces. Only letters, digits and hyphens are used.
  • Shelters: one URI per record. The identifier is register_id, without the hidden character U+FEFF that precedes it in the file (see 1.4). Records are not merged into facilities, because 94 records share street and number with another record (see 1.4) and sharing an address does not prove that they are the same place. Duplicates are handled when counting, not in the URI.
  • Fountains. The identifier is CODI (for example 01-004). The hyphen is valid in a URI.
  • Street trees. The identifier is codi, which is unique in the 145,034 records. It is kept as text because it has leading zeros and letters (0000423AR). The class covers both the 140,271 trees and the 4,763 palms of the file.
  • Tree species. The identifier is the numeric cat_especie_id, because scientific names change (synonyms such as Platanus × acerifolia, also written Platanus × hispanica) and include varieties and cultivars. In the file, each id has exactly one name, so the id is a valid key. The one name with two ids (Ulmus minor 'Umbraculifera', ids 589 and 2764) is given a single URI, built from the lower id (589), in the data preparation; the trees with the id 2764 point to it. The ids are at the level used by the city, which includes cultivars (77 of the 288 names have a cultivar name in quotes, see 1.4), so several species URIs can be linked to the same Wikidata species item. The name stays available as the scientificName property.
  • Neighbourhoods and districts. The identifier is the two-digit code, always kept as text so that 03 is not turned into 3. Neighbourhood 03 and district 03 do not collide because the class name is part of the path. The three datasets share the same 73 neighbourhood and 10 district codes (see 1.3), so one individual serves all of them; a fountain is linked to its neighbourhood and its district is derived from it. The 14 records that have a district but no neighbourhood (10 fountains, 4 trees) get no area link (see 1.4).
  • Shelter categories. A fixed list of CamelCase names (for example Library, SwimmingPool, Market, Other), defined once in the data preparation. The category is derived from the shelter name, because no column of D1 states the type (see 1.4).

3.4 Dereferencing, persistence and external URIs

  • Things and documents. A URI under /resource/ identifies the real-world thing (a shelter, a fountain, a neighbourhood), not a web page about it. A request to such a URI is answered with an HTTP 303 (See Other) redirect to /page/{ClassName}/{identifier} (HTML) or to /data/{ClassName}/{identifier}.ttl (Turtle), depending on the Accept header of the request (content negotiation). Each URI therefore identifies only one item.
  • Ontology. The hash URI .../ontology/HeatRelief returns the documentation or the Turtle file, depending on the Accept header.
  • Status. Content negotiation and redirects are the planned design for the publication of the dataset; they are not deployed in this assignment.
  • Persistence. The URIs contain no server name, no file extension, no query and no version number, so they do not have to change if the hosting changes.
  • Other datasets. The project never mints URIs inside the Wikidata namespace. Neighbourhoods, districts and species are linked to the Wikidata items with owl:sameAs.
