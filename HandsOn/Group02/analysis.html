Dataset & Licensing Analysis

1. Dataset Analysis

We analyzed two datasets from the Chicago Data Portal: CPD_Facilities and CPD_Park_Art. Below are the key findings regarding their schema, quantities and value ranges.

1.1. Chicago Park District Facilities Dataset

Each row is one facility (a playground, a tennis court, a gymnasium, etc.) located in a park.

  • Quantities: 4,467 rows and 9 columns.
  • Null Values: Very clean data. The only missing values are one blank FACILITY_N and one blank FACILITY_T, and both belong to the same row (OBJECTID_1 4482, Gately Park). That row describes no facility and will be removed.
  • Unique Values: 549 distinct park numbers (PARK_NO) but 562 distinct park names (PARK), 75 distinct facility names and 3 facility categories.
  • Data Type Issues:
    • The identifier columns OBJECTID_1, PARK_NO and GISOBJID use a non-breaking space as thousands separator (e.g. 1 111), which is why they import as text.
    • The coordinate columns (X_COORD, Y_COORD) use commas as decimal separators (e.g. -87,52486664).
  • Consistency Issues:
    • Several park numbers appear with more than one name. Most are spelling or formatting variants (MARQUETTE (jACQUES), PALMER ( POTTER), GATELY/GATLEY, MORAN (TERRANCE)/MORAN (TERRENCE)).
    • Some park numbers carry genuinely different parks: 19 (Jackson / Garfield), 168 (Matanky / Renaissance), 213 (Harrison / Stanton). Conversely, Garfield appears under 19 and 204, and Stanton under 109 and 213. Since Park URIs are built from PARK_NO, these rows must be checked and corrected manually.
    • the_geom duplicates X_COORD/Y_COORD, and the two disagree by more than 1 m in 66 rows (up to about 200 m).
    • GISOBJID is not a reliable identifier: it contains two 0 placeholders.
    • The FACILITY_N column has some rows with similar names that represent the same facility (e.g. FITNESS CENTER/FITNESS COURSE).

1.2. Chicago Park District Park Art Dataset

Each row is one public artwork (sculpture, mural, fountain, memorial, etc.) located in a park.

  • Quantities: 346 rows and 11 columns.
  • Null Values: Missing data in ARTIST (15 blanks), OWNER (53 blanks) and OFFICIAL_N (164 blanks).
  • Unique Values: 117 distinct park numbers (119 distinct park names), 325 distinct artwork names and 263 distinct artist values.
  • Data Type Issues:
    • As in the facilities data, PARK_NO and GISOBJID use a non-breaking space as thousands separator, and X_COORD/Y_COORD use commas as decimal separators. The same transformations apply.
  • Consistency Issues:
    • Artists: besides the 15 blanks, 10 rows contain the literal value "Unknown". 55 cells list several artists or a firm (e.g. Frederick & Elisabeth Hibbard, Adler & Sullivan), and the same person is sometimes written differently (Frederick C. Hibbard / Frederick Cleveland Hibbard). Some names contain characters that are not URI-safe (&, commas, ø).
    • Owners: the same organisation appears under several labels (CPD, City of Chicago, COC, City of Chicago & CPD), there are typos (On loan to Notebaert Musuem), and a few owners are individuals.
    • Artwork names: NAME is not unique ("Playground Art" appears 10 times, "Mosaic" 5 times), so it cannot be used in URIs. OFFICIAL_N is an optional formal title: identical to NAME in 122 rows and different in 60, so it is modelled as an alternative label.
    • Parks: a few park names vary under the same number (McKINLEY/MCKINLEY, LINCOLN/LINCOLN (ABRAHAM)), and King Park appears under both 265 and 334.
    • GISOBJID contains 38 placeholder 0 values.

1.3. Relationship Between the Datasets

  • Join key: PARK_NO links both datasets. A park has many facilities and many artworks, so Park is the central entity of the graph.
  • Overlap: 111 of the 117 parks with art also appear in the facilities dataset. The other 6 (e.g. Ogden Plaza, Washington Square, Mid-North) only appear in the art data, so Park resources are generated from the union of both datasets: 555 distinct parks.
  • Name agreement: for 7 park numbers present in both datasets the names never match. Most are spelling variants (PETERSON (PAHR SAMUEL) / PETERSON (PEHR SAMUEL), GARIBALDI (GIUSEPPE) / GARIBALDI (GIUSEPPI)), but parks 115 and 265 carry completely different names and need manual review.

2. Licensing Analysis

  • Publisher: City of Chicago (Chicago Data Portal)
  • Rightsholder: Chicago Park District
  • Original License: The data portal provides the raw datasets under a "Public Domain" designation. However, their Terms of Use states that secondary applications utilizing modified data must feature a specific legal disclaimer acknowledging the City of Chicago as the source and disclaiming liability.
  • Proposed License: Because the source data is Public Domain, we will publish the generated RDF datasets under a Creative Commons Attribution 4.0 International (CC BY 4.0) license. This satisfies the requirement to credit the City of Chicago while allowing the data to be freely shared, linked, and adapted.

3. Resource Naming Strategy

This section defines how URIs are built for the ontology (ontology.ttl) and for the data generated from the two datasets, following the classes and properties defined in the ontology.

3.1. Domain

  • Base Domain: http://smartcity.chicago.es. It is assumed to be a domain owned and controlled by the project, so the URIs can be kept stable and dereferenceable over time.
  • The domain is split into two separate paths: one for the ontology (the vocabulary) and one for the data (the instances).

3.2. URI Form: Hash vs. Slash

  • Ontology: hash URIs. The ontology is small and is published as a single document, so all its terms share one base URI and are distinguished by a fragment (#Artwork, #hasFacility). Retrieving the ontology document returns every term at once.
  • Data: slash URIs. The dataset contains thousands of resources (555 parks, 4,466 facilities, 346 artworks and their artists and coordinates). Slash URIs allow each resource to be requested and described individually, without downloading the whole dataset.

3.3. Ontology URIs

  • Ontology IRI: http://smartcity.chicago.es/ontology/ParkExplorer#
  • Term namespace: http://smartcity.chicago.es/ontology/ParkExplorer# (prefix : in the Turtle files).
  • Classes: UpperCamelCase, singular nouns: :ChicagoPark, :Facility, :Artwork, :Artist.
  • Object properties: lowerCamelCase, verb phrases that read from domain to range: :hasFacility, :hasArtwork, :madeBy.
  • Datatype properties: lowerCamelCase nouns: :parkName, :parkNumber, :facilityName, :facilityType, :facilityGisObjectId, :artworkName, :officialName, :objectId, :artworkGisObjectId, :owner.
  • Every term has an English rdfs:label.

3.4. Reused Vocabulary

Terms reused from other vocabularies keep their original URIs; only new terms are created in the ParkExplorer namespace. The ontology reuses the following terms from schema.org (http://schema.org/, prefix schema:):

  • Classes: schema:Park (superclass of :ChicagoPark), schema:Person (superclass of :Artist), schema:Place (superclass of :Facility and :Artwork) and schema:GeoCoordinates.
  • Properties: schema:geo, schema:latitude and schema:longitude.

3.5. Data (Instance) URIs

All instance URIs follow the pattern http://smartcity.chicago.es/resource/{Entity}/{identifier}, where {Entity} is a fixed, capitalised path segment for each class and {identifier} is taken from the source data.

Ontology Class URI Pattern Identifier Source Example
:ChicagoPark /resource/Park/{PARK_NO} PARK_NO (shared by both datasets, so the same park gets the same URI from either source) .../resource/Park/165
:Facility /resource/Facility/{OBJECTID_1} OBJECTID_1 of the Facilities dataset .../resource/Facility/2494
:Artwork /resource/Artwork/{OBJECTID} OBJECTID of the Park Art dataset .../resource/Artwork/1
:Artist /resource/Artist/{ARTIST_NAME} Artist name converted to a URI-safe slug (the source has no artist identifier) .../resource/Artist/Phil_Schuster
schema:GeoCoordinates /resource/GeoCoordinates/{Entity}_{identifier} Entity and identifier of the facility or artwork the coordinates belong to .../resource/GeoCoordinates/Artwork_1, .../resource/GeoCoordinates/Facility_2494

Rules applied to identifiers:

  • Numeric identifiers are used after cleaning (thousands separators removed), so they appear as plain integers.
  • :ChicagoPark instances use the shorter path segment Park.
  • GISOBJID is not used in URIs because it is missing (0) for some rows; it is kept as a datatype property instead.
  • Artist slugs are built after splitting multi-artist cells and unifying name variants, by replacing every run of characters other than letters and digits with an underscore (e.g. DeStefano & Partners becomes DeStefano_Partners). Blank and "Unknown" artists do not get an Artist URI. Because these URIs are name-based, two different artists with exactly the same name would share a URI, and correcting a name would change its URI.

3.6. Content Negotiation

  • Ontology: a request to http://smartcity.chicago.es/ontology/ParkExplorer returns the Turtle file when the client asks for RDF (Accept: text/turtle), and an HTML documentation page when it is opened in a browser (Accept: text/html).
  • Data: instance URIs identify real-world things (a park, an artwork), not documents, so they are served with a 303 See Other redirect to a document that describes them:
    • Accept: text/turtle (or another RDF format) → http://smartcity.chicago.es/data/{Entity}/{identifier}
    • Accept: text/html → http://smartcity.chicago.es/page/{Entity}/{identifier}
    For example, .../resource/Park/165 redirects to .../data/Park/165 for an RDF client and to .../page/Park/165 for a browser.
